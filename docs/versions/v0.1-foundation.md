# v0.1 — Django + PostgreSQL Foundation

**Status:** Complete  
**Date:** 2026-08-29

## Objective

Build the smallest useful Django application and understand how Django interacts with PostgreSQL. Establish the project structure, development environment, and foundational workflows.

## Features Implemented

- Django project (`config`) and first app (`academics`)
- PostgreSQL connection via environment variables (`.env` file)
- Dedicated PostgreSQL user `campuscore` and database `campuscore`
- `Department` model with `name` (CharField) and `code` (CharField, unique)
- Database migration and schema inspection using `psql`
- Django admin registration for `Department`
- Basic Django view and template to list departments (`/departments/`)
- DRF endpoint `/api/departments/` (list and create)
- Test suite restructured into `academics/tests/` package with separate files for models and API
- Git repository initialized with `.gitignore` and connected to GitHub
- Branching strategy: `main` (stable) and `develop` (ongoing work)
- Documentation (`MASTER_ROADMAP.md` and this file)

## Key Learning Points

- Django project vs app structure and when to create separate apps
- Using `python-dotenv` to load environment variables and keep secrets out of code
- Creating a dedicated PostgreSQL role and database with least privileges
- Why the `CREATEDB` privilege is needed for Django’s test runner (to create test database)
- Model definition: fields, `unique=True`, and how it creates a UNIQUE constraint
- Migration workflow: `makemigrations` → `migrate`
- Inspecting database schema with `psql` meta-commands (`\d`, `\dt`)
- Registering models in Django admin and basic admin customization
- Passing querysets to templates and rendering with Django template language
- DRF basics: `ModelSerializer`, `ListCreateAPIView`, and routing
- Structuring tests in a package for modularity and maintainability
- Git workflow: initializing repository, creating branches, committing, and pushing

## Database Notes

- PostgreSQL role `campuscore` was granted `CREATEDB` solely for local development and testing. In production, use a dedicated test database setup without this privilege.
- The `code` field’s `unique=True` constraint is enforced at the database level, preventing duplicate codes even if application validation is bypassed.

## How to Run

```bash
# Activate virtual environment
source venv/bin/activate

# Run migrations (if not already done)
python manage.py migrate

# Create superuser (if needed)
python manage.py createsuperuser

# Start development server
python manage.py runserver
```

- Web UI: http://127.0.0.1:8000/departments/
- API: http://127.0.0.1:8000/api/departments/
- Admin: http://127.0.0.1:8000/admin/

## Testing

Tests are organized in `academics/tests/`:

- `test_models.py`: model creation and uniqueness constraint
- `test_api.py`: API list and create endpoints

Run tests with:

```bash
python manage.py test
```
